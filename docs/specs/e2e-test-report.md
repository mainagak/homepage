# E2E/受け入れテスト報告

日付: 2026-08-02

対象環境: local。実際のCyberhome/Apache実機・実際のVercelデプロイ先はいずれも
存在しないため、以下の組み合わせで「可能な限り実物に近い」形で検証した。

- 静的ページ: `site/` を Python `http.server`(非CGIモード)でローカル配信し、
  実際のChromium(Playwright)で操作。
- Vercel/FastAPI: `api/app/main.py` を実際に`uvicorn`で起動(ダミー環境変数)。
  ブラウザ側の`VERCEL_API_BASE_URL`は未確定のプレースホルダーのままのため、
  Playwrightの`page.route`で実ブラウザのfetchを実際に動いているこのuvicorn
  インスタンスへ中継する方式(レスポンス本体は手書きモックではなく実際に動いている
  FastAPIコードの出力そのもの)で疎通させた。
- Cyberhome/Perl CGI: `contact.cgi`/`news.cgi`を、Phase 6/7が確立した手法
  (CGI.pm本体がこの環境に無いため、テスト専用の最小限CGI.pmスタブを`PERL5LIB`
  経由で読み込ませる)で実際に子プロセスとして実行し、実際のSTDIN経由のPOSTボディ・
  環境変数を与えて検証した。
- **新たに確認した技術的事実(今回のフェーズで判明):** Windows上のPython
  `http.server --cgi`（`http.server.CGIHTTPRequestHandler`)は、`os.fork()`が
  存在しない環境では`subprocess.Popen([scriptfile])`で`.cgi`ファイルを直接
  `CreateProcess`しようとするため、`OSError: [WinError 193] %1は有効なWin32
  アプリケーションではありません`で必ず失敗することを実機確認した(該当箇所:
  `http/server.py`の`run_cgi()`、`self.have_fork`が偽の分岐)。つまり、この
  Windows環境では「Perlの`.cgi`を実際にHTTP経由でブラウザから叩く」という構成は
  原理的に成立しない(Apache実機以外に代替手段がない)。今後のフェーズでこの
  アプローチを再試行する必要はない。
- Apache Basic認証(`.htaccess`)・実際のsendmail・実際のGoogle reCAPTCHA本番
  キー・実際のFTPSデプロイは、いずれもこの環境に存在せず検証不能(既知の制約、
  `docs/PROJECT_STATUS.md`チェックポイント18・21、`architecture.md`追加質問3〜6と
  同一)。

テスト中に生成した一時ファイル(`site/conf/hmac_secret.txt`、ad-hocの
Playwright specファイル・HTMLフィクスチャ)はすべてテスト後に削除し、
`git status`で追跡対象への副作用がないことを確認済み。

## 発見した問題

### 1. 【重大・新規発見】`contact.html`で`contact-form.js`が実行時エラーで完全に無効化される(reCAPTCHA連携・エラー時再描画・メール確認チェックがすべて機能しない)

**症状:** 実際のブラウザで`contact.html`のJavaScriptコンソールに
`SyntaxError: Identifier 'VERCEL_API_BASE_URL' has already been declared`
が出力される。これにより`js/contact-form.js`ファイル全体が一切実行されない。

**根本原因:** `site/js/chat-widget.js`と`site/js/contact-form.js`は、いずれも
トップレベルで`const VERCEL_API_BASE_URL = '...'`を宣言している。両ファイルとも
`<script src="...">`(非`module`、`defer`なし)として同じ`contact.html`に
読み込まれるため、両者は同一のグローバルレキシカル環境を共有する。同名の
`const`をグローバルスコープで2回宣言すると、2つ目の`<script>`タグの**構文解析
自体が失敗**し(実行時エラーではなくパースエラー)、そのファイル全体が
一切実行されなくなる。これは複数の独立した`<script>`タグが素朴に`const`/`let`を
トップレベル宣言する際によく知られたブラウザの仕様上の挙動であり、Playwrightの
不具合や本テストのセットアップミスではない(実際にChromiumのコンソールで再現を
確認済み)。

**実際に確認した影響:**
- `typeof window.onRecaptchaSuccess === 'undefined'`(実ブラウザのconsole評価で確認)。
  reCAPTCHA v2ウィジェットの`data-callback="onRecaptchaSuccess"`はこの関数を
  呼び出そうとするが存在しないため、実際のユーザーがreCAPTCHAのチェックボックスを
  解いても**何も起きない**(`verify_token`は空のまま、送信ボタンは`disabled`の
  ままで永久に有効化されない)。
- `restoreFieldValues()`が実行されないため、`contact.cgi`がエラー時に埋め込む
  `<span class="value-holder">...</span>`の内容が可視の`<input>`へ一切移し替え
  られない。実際にバリデーションエラーが起きて`contact.html`が再描画されても、
  ユーザーの目には**全項目が空欄のフォームにエラーメッセージだけが表示される**
  (せっかく入力した内容がすべて消えたように見える)。
- `initEmailConfirmCheck()`が実行されないため、メールアドレス(確認用)欄の
  リアルタイム不一致警告も表示されない。

**なぜこれまで検出されなかったか:**
- Phase 6の`node --check`はファイル単体の構文検証のみで、複数ファイルを
  同一ページで読み込んだ際のグローバルスコープ衝突は検出できない。
- Phase 7(システムテスト)はCyberhome↔Vercelの「継ぎ目」(API契約・HMAC・CORS等)
  を対象にしており、ブラウザ側の複数JSファイル間の相互作用は対象外だった。
- 既存の`tests/e2e/public/contact-submission.spec.ts`のシナリオ#4(正常系)は、
  実際のreCAPTCHA解答を模擬する際に`page.evaluate()`で送信ボタンの`disabled`を
  **直接書き換えて**回避する実装になっており、`onRecaptchaSuccess`が本当に
  呼び出し可能かどうかは検証していなかった。シナリオ#4bはブラウザを経由しない
  `request.post()`での直接CGI呼び出しであり、やはりJSの実行状態を経由しない。
  そのため既存の自動テストはいずれもこの不具合を検出できる構造になっていなかった。
- `tests/e2e/public/contact-page.spec.ts`(既存)がチェックする「送信ボタンが
  disabled」は静的HTMLの初期属性であり、JSが正常に動いているかどうかとは無関係に
  常に真になるため、この不具合があっても合格し続ける。

**推奨される修正(フェーズ6への差し戻し内容):** `VERCEL_API_BASE_URL`を
`chat-widget.js`と`contact-form.js`の両方でトップレベル`const`として重複宣言
している構成自体を解消する。例えば (a) 各ファイルの中身全体を即時関数式
(IIFE)で包みファイルごとに独立したスコープを持たせる、(b) 共通設定を1つの
別ファイル(例: `site/js/config.js`、`window.VERCEL_API_BASE_URL = '...'`という
形でグローバルオブジェクトのプロパティとして1回だけ定義)に切り出し、両ファイルが
そこから読み取る、のいずれかが考えられる。修正後は、実際にブラウザで
`contact.html`を開き、コンソールにエラーが出ないこと・`onRecaptchaSuccess`が
呼び出し可能であること・バリデーションエラー再描画時に可視の入力欄へ値が
復元されることを、本レポートと同様に実際のブラウザで確認すること(単体テストの
守備範囲外であるため、ユニットテストの追加だけでは再発防止として不十分)。

形のE2E検証はこの技術スタック(Windows + Python標準ライブラリ)では実現不可能
であることが明確になった(今後のフェーズで同じアプローチを再試行する必要はない)。
Cyberhome実機またはLinux上のApache/mod_cgi環境が用意され次第、
`tests/e2e/public/news.spec.ts`・`basic-auth.spec.ts`を実行すること。
